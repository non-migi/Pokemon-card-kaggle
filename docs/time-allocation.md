# 時間配分レーン(予測4)の設計 — 2026-07-25 起票

> 外部調査の観察: 「上位は重いモデルを読み込みつつ**試合時間をフルに使っている**。おそらくRL＋限定探索。
> それ以外の上位勢は探索を使っていないように見える」(Kaggle Discussion 724362)。
> 我々は600秒中 median **358秒** / p90 427秒 / max 545秒しか使っていない(v4.3a本番315戦)。

## 1. 現行の時間配分(コード実測)

`src/main.py`:

```python
TOTAL_OVERAGE_SEC = 600.0
RESERVE_SEC       =  60.0
BUDGET_DIVISOR    =  50.0
MAX_MOVE_SEC      =   8.0            # agent_config.json

budget = min(8.0, (remaining - 60) / 50)
```

`src/ptcg/bc_search.py`: `MAX_WORLDS = 24`(価値網無効時)、候補は`TOP_K = 5`。

- **序盤**: `(600-60)/50 = 10.8` → **8.0秒でキャップ**。残り460秒を切るまで8秒固定
- **終盤**: 残り200秒なら `(200-60)/50 = 2.8秒`
- つまり **「残りの1/50を使う」一定割合ルール**。枯渇しない代わりに、
  **局面の重要度をまったく見ていない**

### どちらの上限が実際に効いているか

fixed-worlds 2 の400戦が3362秒(-j 8) → 1試合あたり実CPU約67秒、
1試合の判断数が約45なので **1判断あたり約1.5秒 / 2世界 → 1世界あたり約0.75秒**。
8秒の予算では **約10世界**しか回っておらず、上限24世界には**到達していない**。
→ **律速は壁時計であって世界数上限ではない**。時間を増やせば探索は実際に深くなる余地がある。

## 2. 過去の「時間予算は不発」は現アーキテクチャの結論ではない

`docs/experiments.md` の **ゲートG1(2026-07-12)**「時間予算4倍(v2.3)は不発」は、
**v2.x = ヒューリスティック・ロールアウト時代**の測定である(v2.3=543 vs v2.1=606)。
当時の結論は「探索量ではなく探索の質(ロールアウト方策・相手モデル)が律速」で、
その後まさに質を上げてBC×探索(v4.0a)へ移行し、探索は実際に効くようになった
(純BC比58.1%/400、対Grim壁でも純BC 35.5% → 探索 50.0% = **+14.5pt**)。

**したがって「時間を増やしても無駄」は現行agentでは未検証**。棄却済みとして扱わない。

## 3. 実験設計

### Step 1: 探索量の収益はまだ残っているか(これが分岐点)

**壁時計ではなく`fixed_search_worlds`で計算量を変える。** これはCPU負荷に頑健な
プロファイルなので、このリポジトリで繰り返し問題になった壁時計交絡を最初から回避できる。

- `build/v4.3a-fixed8`(8世界) **vs** `build/v4.3a-fixed2`(2世界) の**直接対決**、
  canonical Alakazamミラー、`--profile fixed-worlds`
- 自分同士なので他の差分がゼロ。1回の実行で「4倍の探索量に収益があるか」が出る
- 事前判定:
  - **8世界が有意に勝つ(下限>50%)** → 探索量に収益あり。Step 2(配分の最適化)へ進む
  - **中立(CIが50%を跨ぐ)** → 4倍にしても効かない。**予測4を閉じる**。
    配分を工夫しても原資が効かないので、時間レーン全体を畳む
- 注意: 8世界は2世界の約4倍のコスト。n=200で約1.2時間の見込み

### Step 2: 同じ総時間を重要局面へ寄せる(Step 1が正のときだけ)

現行は全判断に一律8秒。だが判断の多くはBCが自明に決めている
(top-1とtop-2のスコア差が大きい)。**BCのマージンで予算を配分する**:

```
margin = bc_score[top1] - bc_score[top2]
budget = base * g(margin)      # marginが大きい=自明 → 短く、小さい=難しい → 長く
```

総時間は変えずに、難しい判断へ計算を集中させる。実装前に
**実データでmarginの分布**(自明な判断が何割か)を測り、
「上位X%の難局面へY倍」という配分が総時間内に収まるかを確認する。

### Step 2の測定

Step 1と同じく自分同士の直接対決。ただし配分は**壁時計に依存する**ため、
`fixed-worlds`では測れない。`--profile production`(`-j 1`)で単独実行し、
CPU負荷を他ジョブと共有しないこと。

## 4. やらないこと

- `MAX_MOVE_SEC`の単純な引き上げ。長い試合(176step級)は既に545秒使っており、
  一律に増やすと600秒を超えて終盤が0秒になる。**総量ではなく配分**の問題として扱う
- 壁時計A/Bを他の重いジョブと並走させること(過去にload average 38.6で
  fixed-search incompleteが出ている)

---

## Step 1 の結果(2026-07-25 実施) → **予測4を閉じる**

### 実施設計の変更

当初案の「8世界 vs 2世界の直接対決」は**アリーナが正しく拒否した**
(`ValueError: fixed_search_worldsが不一致: [8, 2]`)。`fixed-worlds`プロファイルは
両者の計算量を揃える前提なので、世界数の異なる直接対決は設計上できない。ガードは妥当。
→ **共通の壁**(`build/wall-grim-top8-bc`、純BCなので世界数の指定なし)に両アームを当てる形へ変更した。

### 結果

| アーム | 世界数 | 勝率 | Wilson95% | n |
|---|---:|---:|---|---:|
| `v4.3a-fixed2` | 2 | 50.0% | 45.1–54.9% | 400 |
| `v4.3a-fixed8` | 8 | **55.0%** | **47.3–62.5%** | 160 |

差 **+5.0pt**、2標本z検定 **z=1.07 / p=0.285**。failure 0、`fixed_search_incomplete` 0、
席 P0 46/80・P1 42/80。**事前登録の判定基準「下限>50%」を満たさない → 中立**。

### 判定: 予測4はここで閉じる(統計だけが理由ではない)

1. **統計的に未達**。+5ptを80%検出力で判定するには各アーム約**1,568戦**必要で、
   8世界では約**13.4時間**。残り期間の使い方として割に合わない。
2. **より重要: この+5ptは既にproductionで実現済みの分である**。
   1世界あたり約0.75秒の実測から、production(8秒/手)は**約10世界**を回している。
   つまり 2→8 の比較は「A/B用の弱い設定 → ほぼproduction相当」への改善であって、
   **productionの上に積める伸びしろではない**。
3. **上積みの余地は壁時計で塞がれている**。`MAX_WORLDS=24`まで回すと
   24×0.75 = 約18秒/判断、45判断で約**810秒 > 予算600秒**。
   全判断で24世界は**予算内に収まらない**。
   → 配分を工夫して一部の判断へ寄せても、原資(600秒)が増えないので上限は小さい。

**結論**: 探索量の追加投入で得られるものは、あっても小さく、かつ予算制約で頭打ち。
Step 2(BCマージンによる予算配分)へは進まない。

### 副産物(今後のA/B解釈に効く)

**`fixed2`は production 相当より約5pt弱い可能性がある**(有意ではないが点推定として)。
このリポジトリのローカルA/Bはほぼ全て`fixed2`で行われているので、
**測っている対象は出荷される agent より少し弱い**。差分を見るA/Bでは問題になりにくいが、
「壁に対する絶対勝率」を本番の予測値として使うときは、この分を念頭に置く。
